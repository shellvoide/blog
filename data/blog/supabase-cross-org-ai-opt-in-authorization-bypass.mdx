> <u>**Supabase**</u>

So we left KLUE, our autonomous security engineer, running against Supabase's open-source platform for a few hours. No scanner, no checklist. Just an agent reading the codebase the way a patient reviewer would, endpoint by endpoint, holding the whole application in its head at once.

Supabase is not a target that falls over, and most of what KLUE tried came back a clean negative. But buried in the AI Assistant, the feature that answers questions about your own database in plain English, it caught something quiet and nasty. Quiet enough that Supabase called it _an obscure bug, not easily identified_, about the nicest thing a maintainer ever says about a hole in their own code.

The setting: a control on your Supabase organization decides how much of a project's data may be handed to a third-party AI provider. Set it to `disabled` and nothing about that project should ever reach a model provider again. It is a _promise the platform makes on the owner's behalf_, and this is how an ordinary _member_ could quietly break it, with no elevated role, no forged token, and not one permission check failing along the way.

That is what makes it strange. Most authorization bugs are a **missing** check: you ask for object `42`, the server forgets to confirm it is yours, and hands it over. Here _both_ identifiers were checked, and checked _correctly_. The caller really did belong to the organization they named, and really did have access to the project they named. Nobody ever checked whether the two had anything to do with _each other_, and that is the whole bug.

## The control that was supposed to hold

Supabase's Assistant can read your database schema, your query logs, even row data, and send it to a model provider to answer a prompt. Because that is _real data leaving for a third party_, the platform gates it behind an organization-level setting, `aiOptInLevel`, that an owner sets and that escalates through four postures:

```text
disabled  →  schema  →  schema_and_log  →  schema_and_log_and_data
```

At `disabled`, **nothing** about the project is sent. At `schema_and_log_and_data`, the model provider can receive schema (DDL), query logs, _and actual row data_. It is a deliberate, owner-level governance dial.

There is a second, stricter control layered on top for regulated tenants. Organizations on a HIPAA plan get third-party prompt/completion tracing **suppressed** for any project flagged `is_sensitive`, so prompts and completions for sensitive, HIPAA-covered projects are never exported to a third-party observability vendor. That suppression lives in `isTracingAllowed()`:

```ts
// apps/studio/lib/ai/braintrust-logger.ts
if (projectRegion === undefined || projectRegion.startsWith('eu-')) return false
if (orgHasHipaaAddon === undefined) return false
if (orgHasHipaaAddon && projectIsSensitive !== false) return false // HIPAA suppression
return true
```

Two controls, both _correct-looking_, both doing exactly what an owner would expect. The problem is not the logic. The problem is _where they get their inputs_.

## Two identifiers, authorized in isolation

Four Assistant endpoints share one root cause:

```text
apps/studio/pages/api/ai/sql/generate-v4.ts
apps/studio/pages/api/ai/sql/policy.ts
apps/studio/pages/api/ai/code/complete.ts
apps/studio/pages/api/ai/feedback/rate.ts
```

The clearest instance is `code/complete.ts`:

```ts
if (IS_PLATFORM && orgSlug && authorization && projectRef) {
  const { aiOptInLevel: orgAIOptInLevel } = await getOrgAIDetails({ orgSlug, authorization }) // caller-supplied org
  aiOptInLevel = orgAIOptInLevel
}
const includeSchema = !isClickhouse && aiOptInLevel !== 'disabled'
const { schemas } = await fetchSchemas(includeSchema, { projectRef, connectionString, headers }) // a DIFFERENT org's project
```

Read the two commented lines together. `aiOptInLevel`, the governance posture that decides whether data leaves, is resolved from `orgSlug`, _a value in the request body_. Then `includeSchema` derived from it is used to fetch the schema of `projectRef`, a _different_ value in the same body. Nothing ever checks that `projectRef` belongs to `orgSlug`.

The subtle part, and the reason this passes review, is that each identifier **is** authorized, just on its own. `getOrgAIDetails({ orgSlug, authorization })` and `getProjectAIDetails({ projectRef, authorization })` both forward the caller's token, so the server _does_ confirm the caller belongs to `orgSlug` and _does_ confirm the caller can access `projectRef`. You cannot name an org or a project you have no rights to. What you _can_ do is name two things you both have rights to that have no business being paired, and the server will pair them.

The HIPAA suppression collapses through the exact same seam:

```ts
if (orgHasHipaaAddon && projectIsSensitive !== false) return false // collapses when orgSlug is spoofed
```

Here `projectRegion` and `projectIsSensitive` come from the _real_ project via `getProjectAIDetails({ projectRef })`, but `orgHasHipaaAddon` comes from the _caller-named_ org via `getOrgAIDetails({ orgSlug })`. Name a non-HIPAA organization, and `orgHasHipaaAddon` goes to `false`, the suppression branch never fires, and tracing is re-enabled for a HIPAA-covered, sensitivity-flagged project. _The project's own attributes never changed._ Only the org they were judged against did.

## Enforcement was sound. The input was not.

This is the part that separates a _real_ relational-authz finding from a hopeful one. It would be easy to look at four endpoints leaking schema and conclude the tool-permission machinery was broken. KLUE checked, and it was not. The layer that decides which Assistant tools run at which opt-in level is genuinely well-built and fails closed. The defect is not in the enforcement. It is that the enforcement is _fed an attacker-chosen input_.

## Proving it without touching anyone's data

The proof came in two halves, and the first half touches no live account at all.

**Half one, offline, against the source.** Lift the two guard expressions verbatim out of the codebase and run them with a real project's attributes held _fixed_, while only the organization posture changes. If the outputs flip, the controls are governed by the org and not by the project, which is the whole claim.

```js
// verbatim from apps/studio/lib/ai/braintrust-logger.ts::isTracingAllowed()
function isTracingAllowed(projectRegion, orgHasHipaaAddon, projectIsSensitive) {
  if (projectRegion === undefined || projectRegion.startsWith('eu-')) return false
  if (orgHasHipaaAddon === undefined) return false
  if (orgHasHipaaAddon && projectIsSensitive !== false) return false // HIPAA suppression
  return true
}
const region = 'us-east-1',
  sensitive = true // real project: US, HIPAA-covered, sensitive
console.log(
  'honest  (real HIPAA org):   orgHasHipaaAddon=true  ->',
  isTracingAllowed(region, true, sensitive)
)
console.log(
  'spoofed (attacker org):     orgHasHipaaAddon=false ->',
  isTracingAllowed(region, false, sensitive)
)

const includeSchema = (level) => level !== 'disabled' // exact expression from complete.ts
console.log("owner's setting (disabled):  includeSchema =", includeSchema('disabled'))
console.log(
  'attacker org (permissive):   includeSchema =',
  includeSchema('schema_and_log_and_data')
)
```

```text
=== HIPAA tracing suppression ===
honest  (real HIPAA org):   orgHasHipaaAddon=true  -> false   (false = SUPPRESSED, correct)
spoofed (attacker org):     orgHasHipaaAddon=false -> true    (true = RE-ENABLED for a sensitive HIPAA project => BYPASS)

=== schema-fetch gate (includeSchema = aiOptInLevel !== "disabled") ===
owner's setting (disabled):  includeSchema = false
attacker org (permissive):   includeSchema = true    (true => named project DDL read & sent to the model provider)
```

The project's region and sensitivity flag are _identical_ in both rows. The only thing that moved is which organization's posture was supplied, and _both controls invert_. That is the vulnerability proven at the level of the guard logic itself, with no target involved.

**Half two, live, against our own organizations.** To show it end to end without exposing anyone's real data, we used two organizations and a project we control:

1. In `ORG_B` (which owns `PROJECT_B`), set the AI opt-in level to **Disabled**.
2. Create a second personal organization `ORG_A` and set its opt-in to the most permissive value, `schema_and_log_and_data`.
3. Copy our own dashboard access token from an existing Assistant request in DevTools.
4. Send the request pairing `ORG_A`'s slug with `ORG_B`'s project:

```http
POST https://supabase.com/dashboard/api/ai/code/complete
Authorization: Bearer <my access token>
Content-Type: application/json

{"completionMetadata":{"textBeforeCursor":"select * from ","textAfterCursor":"","prompt":"complete this","selection":""},
 "projectRef":"PROJECT_B","orgSlug":"ORG_A","language":"sql","dialect":"postgres"}
```

`PROJECT_B` belongs to `ORG_B`, whose opt-in is **Disabled**, so no schema for `PROJECT_B` should ever be read or forwarded, regardless of what slug sits in the body. Instead, with `orgSlug=ORG_A` the server derived the _permissive_ posture, set `includeSchema=true`, and the completion came back reflecting `PROJECT_B`'s real table and column names. Swap only `orgSlug` back to `ORG_B` as a control, and the schema is not included. _The server never checked that `projectRef` belonged to `orgSlug`._ The same behavior reproduced on the other three endpoints, each reading `orgSlug` from the same body and applying it to the named `projectRef`.

## What actually leaks

We scope this precisely, because inflating it is how you lose a maintainer's trust on the next submission.

An authenticated user who belongs to a restricted organization, and who _also_ controls any organization with a more permissive posture, can do two concrete things:

- **Exfiltrate governed project data against the owner's policy.** The owner's `aiOptInLevel` (say, `disabled`) is overridden, so the named project's schema, query logs, or actual row data are read and transmitted to third-party AI providers. The data belongs to a project inside the _restricted_ organization, and only ordinary member access is required, with no elevated role.
- **Defeat a compliance control.** The HIPAA tracing suppression that keeps prompts and completions for sensitive projects out of a third-party observability vendor is collapsed by naming a non-HIPAA org, re-enabling that export for _exactly the projects the control exists to protect_. Because the opt-in level is spoofable in the same request, the exported payload can simultaneously be widened to include schema, logs, and rows.

The honest boundary: this is a confidentiality breach of governed and regulated project data to third-party processors, driven by an ordinary org member. It is _not_ a takeover, _not_ a credential leak, and **self-hosted deployments are not affected**, because all four paths are gated behind `IS_PLATFORM`. This is a hosted-platform issue only.

## Why a scanner does not get here, and why review did not

There is _no payload_ for this. A DAST scanner sends a request, gets a response, and grades it against a signature. There is no signature for _"these two body fields were each authorized correctly but should have been checked against each other."_ The bug is not in any single value. It is in an **absent relationship** between two valid values, and absence has no fingerprint.

Static analysis struggles for the same reason. `getOrgAIDetails({ orgSlug, authorization })` is a properly authorized call. `getProjectAIDetails({ projectRef, authorization })` is a properly authorized call. A taint tracker following either one finds a clean, token-checked path and moves on. The defect only exists _in the join_, and the join is a check that isn't written down anywhere to be found.

Even human review, which absolutely _could_ catch this, has to survive a specific trap: every line reads as correct. To see the bug you have to notice that `orgSlug` and `projectRef` arrive from the _same untrusted body_, hold the fact that they are independently authorized, and _still_ ask the one question the code never does. KLUE flagged it in exactly those terms, and then noticed the codebase had no test guarding against it either.

The remediation is small and precise, which is usually the case with relational-authz bugs: before trusting `orgSlug` to govern anything, _confirm that `projectRef` actually belongs to it_. One check, on the relationship, at each of the four call sites, plus the regression test that pins it.

## Disclosure

The finding was reported to Supabase with the full offline and live proof-of-concept, the exact four call sites, and an explicit statement of scope: what the leak does and does not expose, and the fact that self-hosted is unaffected. Supabase triaged it, confirmed it, improved the privacy controls in the hosted platform, and credited the diligence it took to surface it, as their note at the top of this post reflects. _One obscure bug, on a platform that had done nearly everything else right_, found by holding a complete theory of two authorized identifiers in mind long enough to notice the line between them was never drawn.
