follow-redirects is the drop-in redirect engine running underneath axios and a massive slice of the Node HTTP ecosystem. Whenever an application makes an outbound HTTP request and follows a redirect, follow-redirects sits in the middle, rewriting targets and deciding what crosses the wire. And when a redirect jumps across origins or downgrades from HTTPS to HTTP, follow-redirects has one critical job: make sure sensitive headers like Authorization and Cookie do not follow along.

The maintainers had already patched this boundary across several prior disclosures: CVE-2022-0155 added cross-origin stripping for `Authorization`, CVE-2022-0536 extended it to `Cookie`, and CVE-2026-40895 (GHSA-r4q5-vmmm-2653) added `options.sensitiveHeaders` so callers could declare custom secret headers beyond the built-in set.

During an autonomous security review with KLUE, our security agent, we identified two independent flaws that cause this stripping control to fail open without throwing an error or logging a warning:

1. **A container type-mismatch defect (CVE-2026-111756):** Node's HTTP client accepts headers as an alternating array as well as an object. When headers are passed as an array, the stripping routine iterates array indices (`"0"`, `"1"`, ...) instead of header names, causing all credential headers to be forwarded to the redirect target.
2. **An incomplete regex escaper (CVE-2026-111755):** The `sensitiveHeaders` option constructs a regular expression alternation but fails to escape `^` and `|`. Both are valid HTTP token characters under RFC 9110 and accepted by Node. A custom header containing either character corrupts the alternation, exempting the secret from stripping and collaterally dropping unrelated headers.

The short version: if an application makes outbound requests through follow-redirects (directly or via axios) and follows a cross-origin redirect, both flaws can silently hand credentials to the destination.

## Which headers actually get stripped

The failure in both vulnerabilities is completely silent. An application receives normal HTTP responses, and the request completes without errors:

| Header configuration | What you expect on cross-origin redirect | What actually reaches the destination | Verdict |
| --- | --- | --- | --- |
| Object headers: `{ Authorization: "Bearer ..." }` | Stripped before redirect | Stripped | Protected |
| Array headers: `["Authorization", "Bearer ..."]` | Stripped before redirect | **Forwarded verbatim** | **Leaked (CVE-2026-111756)** |
| Standard custom: `sensitiveHeaders: ["X-Api-Key"]` | Stripped before redirect | Stripped | Protected |
| Metacharacter anchor: `sensitiveHeaders: ["X-Api^Key"]` | Stripped before redirect | **Forwarded verbatim** | **Leaked (CVE-2026-111755)** |
| Metacharacter pipe: `sensitiveHeaders: ["X-Token\|Secret"]` | Stripped before redirect | **Forwarded verbatim** | **Leaked (CVE-2026-111755)** |
| Unrelated header: `X-Token: "harmless"` (with above) | Sent to destination | **Stripped by mistake** | **Collateral drop** |

## How KLUE found both flaws

KLUE traces execution paths from API entry points down to low-level runtime sinks. When analyzing follow-redirects, it evaluated `RedirectableRequest` against the full specification of Node's HTTP client and RFC 9110.

Two specific questions uncovered the flaws:

1. In `removeMatchingHeaders`, the code performs `for (var header in headers)`. What happens when the input container is an `Array` rather than an `Object`?
2. In `escapeRegex`, the code uses a character class replacement before compiling an alternation pattern. Which valid RFC 9110 header token characters are absent from that character class, and what AST does the JavaScript RegExp engine produce when those characters are present?

Every finding KLUE produces is validated by an engineer on our team. We reproduced both vectors against follow-redirects 1.16.0 with isolated HTTP/HTTPS test fixtures, verified the network captures, and confirmed the exact failure points before reporting them to the maintainers.

## Finding 1: Array-form headers bypass removeMatchingHeaders (CVE-2026-111756)

**In plain terms:** Node's `http.request` accepts headers as an array of alternating names and values. follow-redirects iterates headers with `for...in`, which evaluates to numeric string indices (`"0"`, `"1"`, ...) on arrays. The regex never matches numbers, so zero headers are removed, and credentials travel to the redirect target.

### Node's Dual Header Representation

Most developers pass headers to Node's HTTP client as a plain key-value object. But Node's standard library has long supported a second format: an alternating flat array.

In Node's native HTTP implementation (`lib/_http_outgoing.js`), the outgoing request constructor handles both representations:

```js
// Node.js lib/_http_outgoing.js
if (Array.isArray(headers)) {
  for (let i = 0; i < headers.length; i += 2) {
    this.setHeader(headers[i], headers[i + 1]);
  }
} else if (headers) {
  for (const key of Object.keys(headers)) {
    this.setHeader(key, headers[key]);
  }
}
```

Applications and HTTP middleware use the array format when they need exact control over header serialization order on the wire, or when sending duplicate header keys (such as multiple `Set-Cookie` or `Cookie` lines).

### The Property Enumeration Failure

When follow-redirects receives a 3xx response in `_processResponse`, it calls `removeMatchingHeaders` at `index.js:630-640` to strip credentials:

```js
function removeMatchingHeaders(regex, headers) {
  var lastValue;
  for (var header in headers) {        // for...in over an array yields "0", "1", "2"...
    if (regex.test(header)) {          // the header-name regex never matches a numeric index
      lastValue = headers[header];
      delete headers[header];
    }
  }
  return (lastValue === null || typeof lastValue === "undefined") ?
    undefined : String(lastValue).trim();
}
```

In ECMAScript, an `Array` is an exotic object whose property names are string representations of unsigned integers (`"0"`, `"1"`, `"2"`, ...). The `for...in` statement iterates an object's enumerable string property keys.

When `headers` is an array like `["Authorization", "Bearer secret"]`, the variable `header` iterates `"0"` and `"1"`. It never contains `"Authorization"`.

During a cross-origin redirect, `regex` is `this._headerFilter`:

```text
/^(?:authorization|proxy-authorization|cookie)$/i
```

The runtime loop evaluates:

- `regex.test("0")` -> `false`
- `regex.test("1")` -> `false`

The test condition is never met. `delete headers[header]` never executes. The function returns `undefined`, and the unmodified array in `this._options.headers` is forwarded directly to `nativeProtocol.request(this._options)` at `index.js:352`.

### Secondary Protocol Defects

Because `removeMatchingHeaders` is used across all header-sanitization paths, two additional protocol defects occur on array-form requests:

1. **Stale Host header (`index.js:470`):** `removeMatchingHeaders(/^host$/i, this._options.headers)` fails to strip the previous origin's `Host`. The redirected request transmits the old host to the new server, violating RFC 9110 Section 7.2 and corrupting virtual-host routing.
2. **POST-to-GET Content-Length mismatch (`index.js:466`):** On 301, 302, or 303 redirects where a POST is rewritten to a bodyless GET, `removeMatchingHeaders(/^content-/i, this._options.headers)` fails. The outgoing GET retains the original `Content-Length` header with an empty payload, causing HTTP request desynchronization or `400 Bad Request` responses on reverse proxies.

## Finding 2: Incomplete regex escaping in sensitiveHeaders (CVE-2026-111755)

**In plain terms:** The `sensitiveHeaders` option protects custom headers by compiling their names into a regular expression. The escaping function fails to escape `^` and `|`. Both are valid header-name characters under RFC 9110 and accepted by Node. A header name containing either character breaks the regular expression, allowing the secret header to pass through on redirect.

To implement `sensitiveHeaders` in version 1.16.0, follow-redirects compiles an alternation pattern inside the `RedirectableRequest` constructor at `index.js:118-120`:

```js
this._headerFilter = new RegExp("^(?:" +
    sensitiveHeaders.concat(options.sensitiveHeaders).map(escapeRegex).join("|") +
  ")$", "i");
```

Before joining names with `|`, each name is passed through `escapeRegex` at `index.js:703-705`:

```js
function escapeRegex(regex) {
  return regex.replace(/[\]\\/()*+?.$]/g, "\\$&");
}
```

The character class escapes ten characters: `]`, `\`, `/`, `(`, `)`, `*`, `+`, `?`, `.`, and `$`. It omits five ECMAScript RegExp syntax characters: `^`, `|`, `[`, `{`, and `}`.

### RFC 9110 Token Grammar and Node Validation

RFC 9110 Section 5.6.2 defines the grammar for HTTP header field names:

```text
field-name     = token
token          = 1*tchar
tchar          = "!" / "#" / "$" / "%" / "&" / "'" / "*"
               / "+" / "-" / "." / "^" / "_" / "`" / "|" / "~"
               / DIGIT / ALPHA
```

Both `^` (ASCII 0x5E) and `|` (ASCII 0x7C) are valid `tchar` characters.

In Node's `lib/_http_common.js`, incoming and outgoing header names are validated with `checkIsHttpToken`. Node permits `^` and `|` in header names and rejects `[`, `{`, and `}` with `ERR_INVALID_HTTP_TOKEN`.

Because Node accepts `^` and `|`, an application can legitimately send headers like `X-Api^Key` or `X-Token|Secret`.

When an application passes these names into `sensitiveHeaders`, the unescaped characters alter the RegExp AST:

```text
^(?:Authorization|Proxy-Authorization|Cookie|X-Api^Key|X-Token|Secret|X-Control-Key)$
                                                  ^          ^
                                                  |          \-> Pipe splits into two bogus alternatives
                                                  \............> Mid-string anchor can never match
```

### Pattern Failure Modes

1. **Mid-Pattern Start Anchor (`^`):** In `X-Api^Key`, the `^` character acts as a start-of-input anchor. In the compiled pattern `^(?:...|X-Api^Key|...)$`, matching `X-Api` consumes five characters. The subsequent `^` asserts that the current index is position 0. That condition is impossible to satisfy after consuming characters. As a result, `test("X-Api^Key")` returns `false`, and the header is never stripped.
2. **Alternation Operator Splitting (`|`):** In `X-Token|Secret`, the unescaped `|` acts as an alternation operator with the lowest operator precedence. The single header name is split into two independent branches: `X-Token` and `Secret`. The real header `X-Token|Secret` matches neither branch and is not stripped. Collaterally, if the request contains unrelated headers literally named `X-Token` or `Secret`, follow-redirects matches and strips them by mistake.
3. **Invalid Token Crash (`[`, `{`, `}`):** If an application declares an entry containing `[`, `{`, or `}`, Node will not send it as a live header, but the unescaped bracket injects an unterminated character class or quantifier into the regex. The constructor throws a `SyntaxError`, failing the request immediately.

### Secondary Lifecycle Weakness

`this._headerFilter` is instantiated once in the `RedirectableRequest` constructor at line 118. When a redirect occurs, `removeMatchingHeaders` is called at line 490 before the `beforeRedirect` hook is invoked at line 494. If an application mutates `options.sensitiveHeaders` inside `beforeRedirect`, the filter is never recompiled, and newly added headers are ignored.

**Classification.** CWE-185 (Incorrect Regular Expression), CWE-200 (Exposure of Sensitive Information to an Unauthorized Actor). Assigned **CVE-2026-111755**, published as [GHSA-8r9p-f939-6h3c](https://github.com/follow-redirects/follow-redirects/security/advisories/GHSA-8r9p-f939-6h3c). Affects version `1.16.0`. Fixed in `1.16.1`.

## Root-cause analysis: Why both controls failed open

Both vulnerabilities share a common failure pattern: the implementation relied on narrow assumptions about runtime input types and character sets.

1. **Unchecked Container Types:** In JavaScript, `for...in` iterates property keys across any object type. Because arrays are objects with numeric string keys, iterating an array with `for...in` executes without throwing a `TypeError`. The control assumed `headers` was always a key-value record, failing to account for Node's dual-representation HTTP interface.
2. **Partial Metacharacter Escaping:** When compiling dynamic strings into a regular expression, escaping must cover all ECMAScript RegExp syntax characters (`^ $ \ . * + ? ( ) [ ] { } |`). Escaping ten characters while omitting five created an incomplete sanitization boundary. Because RFC 9110 permits characters from that omitted set, valid protocol inputs corrupted the pattern syntax.
3. **Test Suite Blind Spots:** In the follow-redirects test suite, unit tests for `sensitiveHeaders` only asserted alphanumeric names (`Sensitive-A`, `x-sensitive-b`). Tests for redirect stripping only exercised plain object headers. The test coverage validated the happy path of the author's mental model, leaving valid protocol permutations untested.

## How 1.16.1 fixes both flaws

The upstream patch in `follow-redirects 1.16.1` addresses both issues directly at their root:

### 1. Array support in removeMatchingHeaders

Instead of assuming `headers` is an Object, `removeMatchingHeaders` now checks `Array.isArray(headers)`. For arrays, it iterates in step-2 increments and splices matched pairs from the array:

```diff
 function removeMatchingHeaders(regex, headers) {
   var lastValue;
-  for (var header in headers) {
-    if (regex.test(header)) {
-      lastValue = headers[header];
-      delete headers[header];
-    }
+  if (Array.isArray(headers)) {
+    for (var i = 0; i < headers.length; i += 2) {
+      if (regex.test(headers[i])) {
+        lastValue = headers[i + 1];
+        headers.splice(i, 2);
+        i -= 2;
+      }
+    }
+  } else {
+    for (var header in headers) {
+      if (regex.test(header)) {
+        lastValue = headers[header];
+        delete headers[header];
+      }
+    }
   }
   return (lastValue === null || typeof lastValue === "undefined") ?
     undefined : String(lastValue).trim();
 }
```

### 2. Complete RegExp escaping

`escapeRegex` was updated to include all ECMAScript RegExp metacharacters:

```diff
 function escapeRegex(string) {
-  return string.replace(/[\]\\/()*+?.$]/g, "\\$&");
+  return string.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");
 }
```

## Impact and downstream exposure

Both bugs are information-disclosure vulnerabilities affecting confidentiality during cross-origin redirection:

- **CVE-2026-111756 (Array Headers):** Leaks all credential headers (`Authorization`, `Cookie`, `Proxy-Authorization`, and all `sensitiveHeaders`). Additionally causes stale `Host` header re-transmission and `Content-Length` mismatches on POST-to-GET redirects.
- **CVE-2026-111755 (Regex Escaping):** Leaks declared custom headers containing `^` or `|`. Built-in headers remain stripped on object-form requests.
- **Downstream Reach via axios:** Because axios delegates HTTP redirect handling directly to follow-redirects, axios applications inherit both vulnerabilities whenever request options pass through to the underlying redirector.
- **Cleartext Downgrades:** On HTTPS-to-HTTP redirects, leaked credentials travel in cleartext over the wire, exposing them to passive network observers.

## Mitigation

Upgrade to **follow-redirects 1.16.1**, which resolves both CVEs.

If you cannot upgrade immediately:

- Pass headers exclusively as plain JavaScript objects. Avoid array-form headers when making requests through follow-redirects or axios.
- Avoid using `^` or `|` in custom sensitive header names, or sanitize them before configuring `options.sensitiveHeaders`.
- If using axios, ensure dependencies resolve to `follow-redirects >= 1.16.1`.
