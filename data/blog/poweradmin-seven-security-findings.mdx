Poweradmin is the web interface a large share of PowerDNS operators run in front of their nameservers. It is a PHP application, and it does the ordinary work of a DNS control panel: add and edit records, sign zones, rotate DNSSEC keys, and hand each customer a slice of the server to manage. The last part is the one that matters for security. Poweradmin is built to be multi-tenant, with a permission model whose entire job is to keep a customer inside their own zones, out of everyone else's, and well away from the DNS server itself. Permission templates like Guest, Viewer, Editor, and Zone Manager are how an operator draws those lines.

We pointed KLUE, our security agent, at Poweradmin to see whether those lines actually held. They did not, in seven different places. The worst gives a tenant with the shipped Zone Manager role code execution as root on the DNS server, through a PowerDNS LUA record. Four more end in a full `user_is_ueberuser` account: two through single sign-on, two through the ordinary user-creation path. The last two are narrower but still serious: a restricted editor rewriting a zone's SOA and NS records, and an attacker toggling a zone's DNSSEC key through a GET that a logged-in operator's browser can be made to send.

The short version: six of the seven are checks that fail open, and most of them fail open toward Administrator. The seventh, the LUA record, is the one that makes the rest serious, because it turns a tenant account into control of the DNS server every other tenant depends on. The maintainers confirmed all seven and shipped fixes across the maintained branches. Four were assigned CVEs, all rated High. The other three, including the Critical code execution, are fixed with CVEs still pending.

## How it was found

It started the way every one of our runs does. We set KLUE, our security agent, reading Poweradmin, and it worked through the code the way a careful reviewer would, reasoning about what each check protects rather than scanning for patterns or firing requests at a running instance. The permission model was the natural place to spend that attention, because it is the thing standing between a tenant and everything they are not meant to reach. So KLUE walked it boundary by boundary and asked, at each one, what happens when the input is missing or attacker-shaped: when the default template cannot be resolved, when the SSO token carries an address the provider never verified, when two parts of the same request disagree about what is being edited, when a security helper is reached on a code path the guard was never wired to.

That is where our team takes over, which is the part we care about most, because we do not take KLUE's word for anything. Every bug it surfaced went to an engineer on our side who reproduced it from scratch on a self-hosted Poweradmin build before it counted as a finding at all. For these seven that meant standing up the panel against a real PowerDNS backend, logging in as low-privilege tenants, and driving each path end to end: writing the metadata row and watching `id` run as root, deleting the Guest template and watching a new SSO user land as a superuser, submitting a type-swapped record and reading the overwritten SOA back out of the database. Only the ones that held up that way were written up and sent to the maintainers, and everything below is one of those.

## Finding 1: a Zone Manager can run code as root on the DNS server

**In plain terms:** PowerDNS can hold a record whose value is a LUA script, and it runs that script to answer a query. A tenant with the shipped Zone Manager role can turn that feature on for a zone they own, then store a record whose script runs an OS command. The command runs as the PowerDNS user, which on a default install is root.

Three separate weaknesses line up to make this reachable by a tenant who holds `zone_meta_edit_own` and `zone_content_edit_own` but not `user_is_ueberuser`.

First, the control that is supposed to stop a tenant setting dangerous metadata only runs on one backend. In `EditZoneMetadataController::saveMetadata()`, the `api_write` filter is applied only when the request goes through the API client. The default `dns.backend = 'sql'` takes the other branch and writes the row straight through `replaceDomainMetadata()` with no filter at all. Second, `resolveSubmittedKind()` uppercases and trims the submitted metadata kind and returns it without checking it against `MetadataDefinitions::DEFINITIONS` or testing `api_write`, and the UI dropdown offers `ENABLE-LUA-RECORDS` as a normal option. So the tenant can enable LUA evaluation on their own zone.

Third, the content check for LUA records is a regex blocklist:

```php
// LUARecordValidator::validateLuaContent()
/\b(os\.|io\.|file\.|loadfile|dofile)\b/i
```

A regex cannot contain a Turing-complete language. Any of table indexing, `require`, or string concatenation walks around it, so `os.execute` is rejected while the same call reached indirectly is accepted.

A related template-record validation gap is tracked separately as GHSA-c859-jm5r-62x6.

## Finding 2: single sign-on links accounts by an email nobody verified

**In plain terms:** Poweradmin can log you in through OIDC or SAML and link the external identity to a local account by email address. It never reads the `email_verified` claim. So an attacker who can make a trusted provider assert an arbitrary email, while holding only their own ordinary identity, can log in as the local account that owns that address, up to and including a superuser.

This is the nOAuth pattern, and in Poweradmin it comes from three properties lining up. The `email_verified` claim is never read anywhere in `lib/`. Linking is on by default, because the code reads the flag as `($authConfig['link_by_email'] ?? true)`, so a provider entry that omits the key still gets it. And the lookup that finds the account to link to, `findUserByEmail()`, filters only on `active = 1`: it does not exclude local password accounts, permission templates, or accounts holding `user_is_ueberuser`.

The flow runs through `UserProvisioningService::provisionUser()`. On a first login there is no existing subject link, so the email branch runs, `findUserByEmail()` returns the matching account, and `linkOidcToExistingUser()` persists a row in `oidc_user_links` binding the attacker's subject to that account. `updateExistingUser()` then overwrites the account's fullname and email from the assertion and returns the existing user ID, which becomes the session user.

Affects 4.1.0 through 4.2.5, 4.3.0 through 4.3.4, and 4.4.0. Fixed in `4.2.6`, `4.3.5`, and `4.4.1`. Advisory: [GHSA-h2h8-xprp-w5cc](https://github.com/poweradmin/poweradmin/security/advisories/GHSA-h2h8-xprp-w5cc).

## Finding 3: when the default template cannot be resolved, the default is Administrator

**In plain terms:** when Poweradmin auto-provisions a user from OIDC or SAML, it picks the new account's permission template. If the configured default template name cannot be matched, it does not stop and it does not pick the lowest role. It falls back to the first row in the table, which on every shipped install is the Administrator template.

The choice happens in `UserProvisioningService::determinePermissionTemplate()`. It calls `findPermissionTemplateByName()` with the configured default. On a miss it logs an error, logs the warning "Default permission template not found, using first available template", and calls `findFirstAvailablePermissionTemplate()`:

```sql
SELECT id FROM perm_templ ORDER BY id ASC LIMIT 1
```

The bundled schema seeds `perm_templ` id 1 as `Administrator`, which holds `perm_id 53 = user_is_ueberuser`. `findPermissionTemplateByName()` does a case-sensitive exact match (`WHERE name = ?`), and nothing validates the configured name at boot or at login, so the miss is easy to cause: rename or delete the Guest template, or set `default_permission_template` to `'guest'` instead of `'Guest'`. `createNewUser()` calls this with `$useDefaultFallback = true` by default and writes the returned id straight into the new user's `perm_templ` with `active = 1`.

Advisory: [GHSA-vw9h-w6h7-9wwm](https://github.com/poweradmin/poweradmin/security/advisories/GHSA-vw9h-w6h7-9wwm).

## Finding 4: the "minimal" permission template is Administrator

**In plain terms:** there is a helper whose job is to return the least-privileged template, the safe default for a caller that is not trusted to choose one. It ranks templates by how many permission rows they have, and because `user_is_ueberuser` is a single row, the Administrator template has the fewest. Delete the Guest template and "minimal" becomes admin.

`UserManager::getMinimalPermissionTemplateId()` ranks with:

```sql
SELECT id FROM perm_templ pt ... ORDER BY perm_count ASC, pt.name ASC LIMIT 1
```

Row counts on the shipped schema make the problem concrete:

| Template | Rows in `perm_templ_items` |
| --- | --- |
| Guest | 0 |
| Administrator | 1 |
| Viewer | 2 |
| Editor | 4 |
| Zone Manager | 11 |

Guest has zero rows and normally wins, so the helper works. With Guest gone, Administrator has the lowest count and is returned as "minimal". `PermissionTemplateAssignmentGuard::apply()` then uses that result as the default for callers without template-assignment rights. The guard correctly rejects an explicit `perm_templ` from a caller that lacks `user_edit_templ_perm` or `user_is_ueberuser`, which is what stops a `user_add_new` holder from naming the admin template directly. The bug is the other half: if `perm_templ` is omitted, the guard injects the helper's result into the input, and the helper is now returning Administrator.

## Finding 5: the SOA/NS rule checks the record type the attacker sends, not the one being overwritten

**In plain terms:** one permission lets a customer edit the records in their own zone but keeps them off the SOA and NS records. The check looks at the record type in the request. Submit an edit for an existing SOA or NS record but label it as an `A` record, and the check passes while the write still lands on the protected row.

The bug is in `RecordManager::editRecord()`. It loads the existing record with `$recordRepository->getRecordDetailsFromRecordId($record['rid'])`, which includes the record's real stored type, but it uses that result only to set `$record['zid']`. When `$perm_edit == "own_as_client"`, the guard compares only `$record['type']`, the type submitted in the request, against `SOA` and `NS`. It never looks at the type of the record actually being modified.

The API gets this right. `Api/V2/ZonesRecordsBulkController::performUpdateOperation()` checks both the existing type (through `permissionService->canEditZoneRecord`) and the requested new type, and returns a 403 "You do not have permission to edit this record type" on failure. That the web form and the API disagree is what marks the web behavior as a defect rather than intended design.

Advisory: [GHSA-3h74-qh4c-64gg](https://github.com/poweradmin/poweradmin/security/advisories/GHSA-3h74-qh4c-64gg).

## Finding 6: a DNSSEC key toggle that any GET can trigger

**In plain terms:** the controller that enables and disables a zone's DNSSEC signing key answers a plain GET and performs the toggle with no CSRF token. A logged-in operator who opens an attacker's page can be made to flip the key, which can take a zone's validation down.

`DnssecToggleKeyController`, in `lib/Application/Controller/DnssecToggleKeyController.php`, serves `GET|POST /zones/{zone_id}/dnssec/keys/{key_id}/toggle`. It validates the numeric ids and zone-edit permission, then toggles immediately, calling `deactivateZoneKey()` if the key is active and `activateZoneKey()` otherwise. There is no `confirm` step. Poweradmin has a working CSRF mechanism, `CsrfTokenService` with a random token in `$_SESSION['csrf_token']` compared by `hash_equals`, and the destructive controllers that use it wrap the action the usual way:

```php
// the pattern in DeleteRecordController, DeleteDomainController, DeleteUserController, ...
if ($this->isPost()) {
    $this->validateCsrfToken();
    // ... perform the action
}
```

`DnssecToggleKeyController` omits both the `isPost()` gate and `validateCsrfToken()`. `SameSite=Lax` does not save it: the session cookie is set `SameSite=Lax`, which still rides along on cross-site top-level GET navigations such as `window.location`, an `<a target="_blank">`, a `<meta http-equiv="refresh">`, or a 302 from the attacker's server. It only blocks cross-site subresource loads like `<img src>`.

## Finding 7: the installer decides who is local from a header the client sends

**In plain terms:** the installer can be restricted to a set of IP addresses. It reads the client's address out of the `X-Forwarded-For` header, which the client fills in, so a remote attacker can claim an allowed address and walk through setup.

The weak code is `InstallSecurityService::getClientIp()` in `install/helpers/InstallSecurityService.php`, feeding `checkIpAccess()`. When the allow-list is on (the shipped entry is `127.0.0.1`), `getClientIp()` reads `X-Forwarded-For` whenever it is present, with no trusted-proxy concept and no regard for `REMOTE_ADDR`. It takes the last comma-separated element with `end()`, which is fully attacker-controlled, and if that is a valid IP it returns it. `checkIpAccess()` then compares that value to the allow-list, so a request carrying `X-Forwarded-For: 127.0.0.1` passes. Taking the last element also inverts normal proxy semantics, where the real client is the leftmost entry, so a genuinely proxied request from an allowed client is the one that gets rejected.

Poweradmin already has a correct version of this function elsewhere. `lib/Infrastructure/Utility/IpAddressRetriever::getClientIp()` only consults forwarded headers when `REMOTE_ADDR` is itself private or reserved. The installer ships a separate, weaker copy of the same job.

The window is specific: `ip_access.enabled` ships as `false`, so this only matters for operators who turned the allow-list on, and `Installer::run()` aborts every step but the last once `config/settings.php` exists ("There is already a configuration file in place"). The exposure is the gap between deploying the code and finishing configuration. In that gap an unauthenticated remote attacker can reach every install step, point the installer at a database, apply the schema, and create an administrator with a chosen password; if they can also authenticate to that database (for example with credentials sitting in a compose file) the result is persistent superuser control of every zone. The official container images exclude `install/` through `.dockerignore` and are not affected the same way; source, archive, and git-checkout deployments are.

## Why these happened

None of these is exotic, and that is the point. Six of the seven are the same mistake in different places: a check that resolves a missing or attacker-controlled input by allowing it instead of refusing. The default template cannot be found, so grant the first row. The email is unverified, so trust it. The "minimal" role is ranked by a proxy that happens to favor the admin template, so hand it out. The record type is read from the request instead of the row, the client IP from a header instead of the connection, and the DNSSEC toggle from a GET with no token. In almost every case the safe answer was already implemented somewhere else in the same codebase: the API path checks both record types, `IpAddressRetriever` reads forwarded headers correctly, and the delete controllers all validate a CSRF token. The bug was a second, weaker path that skipped the control the maintainers had already built.

That is the kind of thing KLUE is good at finding, because it does not stop at "there is a check here, good." It asks what the check assumes, whether the same capability is reachable by a path the check does not cover, and what the code does when the assumption is false, and then it goes and tries it. A person on our side reproduced every one of these on a real install before it left the building. That is the division of labor we rely on: the agent reads the whole surface and asks the awkward questions, and an engineer confirms the answer before anyone else hears about it.

## Impact

The seven do not all land in the same place:

- **Code execution (Finding 1).** A tenant with the shipped Zone Manager role runs commands as the PowerDNS user, which on a default install is root. That reaches `pdns.conf`, the backend credentials and API key, the DNSSEC keys, every zone the server is authoritative for, and the ability to stop the service. On a multi-tenant install it is a full break out of the tenancy.
- **Administrator takeover (Findings 2, 3, 4).** Three separate paths end in a `user_is_ueberuser` account: SSO linking by unverified email, SSO provisioning falling back to the admin template, and the user-creation guard injecting the admin template as its "minimal" default. Any one of them yields control of all zones, users, templates, API keys, and DNSSEC operations.
- **Zone-apex tampering (Finding 5).** A restricted customer rewrites their own zone's SOA or NS records, which takes the zone down or removes a mandated nameserver.
- **DNSSEC outage (Finding 6).** An attacker page that a logged-in operator visits deactivates a zone's signing key, making the zone BOGUS for validating resolvers while it still looks healthy in the panel.
- **Installer takeover (Finding 7).** In the window before configuration is finished, an unauthenticated remote attacker reaches the installer and can create an administrator and point the app at a database of their choosing.

## Mitigation

The fixes are out. Upgrade to a patched release for your branch: **3.9.12** on 3.x, or **4.2.6**, **4.3.5**, or **4.4.1** on 4.x. Beyond upgrading:

- If you run Poweradmin multi-tenant, treat this as urgent. The LUA-record bug is a tenant-to-root break, which is the one thing a multi-tenant setup exists to prevent.
- If you use OIDC or SAML, after upgrading set `link_by_email` to false, require verified emails at the provider, and confirm your configured default permission template exists, matches its name exactly, and is not the Administrator template. Audit `oidc_user_links` for subject bindings to privileged accounts you did not create.
- Make sure the installer is not reachable. It should be removed or locked once setup is done, regardless of the `X-Forwarded-For` fix. Container images built from the official Dockerfiles already exclude `install/`.
